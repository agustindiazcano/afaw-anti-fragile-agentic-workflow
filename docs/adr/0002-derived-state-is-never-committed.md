# Shared views are derived from per-task files on demand and never committed

## Context
Version 1.0 committed `state/pending.json` and the `lastcontext.json` files, regenerated by
CI after every merge through a second pull request that the human also approved. That doubled
the review load, let bot pull requests race each other, and left stale copies on working
branches. The files were a pure function of the per-task files, so storing them added nothing.

## Decision
`scripts/build_state.py` builds every shared view (pending, history, metrics, the
`LASTCONTEXT.md` files, the dashboard) from the task files, deltas, ADRs and gotchas at a git
ref, into `build/`, which is ignored by git. The reference time is an explicit input, so the
same ref, facts and time give byte-identical output. Measured facts (timestamps, CI results)
come from git and the CI API through `scripts/collect_facts.py`; task files may not declare
them.

## Alternatives considered
- Keep committing the views, serialized by a CI concurrency group: removes the race but keeps
  the extra pull request and the stale copies.
- A database or an external tracker: another system to run, and state stops being reviewable
  in the pull request.

## Consequences
No shared file is written by two agents, so state cannot conflict. An agent sees only merged
work: two agents can start overlapping tasks, and `PENDING.md` is the guard. Task identifiers
must be unique across parallel branches, which `check_task_files.py` enforces.
